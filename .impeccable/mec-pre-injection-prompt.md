# MECE 前置引導 Prompt 模板庫

**版本：** V1.0  
**最後更新：** 2026-08-22  
**用途：** 在大模型執行 MECE 拆解任務前自動注入，約束輸出邏輯

---

## 1. 通用 MECE 拆解前置引導（所有場景適用）

```markdown
請執行 MECE（Mutually Exclusive, Collectively Exhaustive）結構化拆解任務。

## 你的任務
對以下問題進行系統性根因分析/拆解，確保分析結果符合 MECE 原則。

## 步驟化指令

### Step 1: 確定分析維度
請從以下 6 個標準維度中選擇适用的維度組合：
1. 【技術層面】— 與代碼、配置、架構、選擇器、依賴庫直接相關的因素
2. 【流程層面】— 與開發、測試、部署、審核、CAPA 相關的流程因素
3. 【工具層面】— 與 lint、測試框架、CI/CD、自動化工具相關的因素
4. 【測試驗證層面】— 與單元測試、集成測試、E2E、可訪問性測試相關的因素
5. 【文檔層面】— 與規格文檔、設計規範、日誌記錄、知識傳承相關的因素
6. 【環境層面】— 與瀏覽器、設備、部署環境、快取策略相關的因素

### Step 2: 逐維度拆解
對每個选定的維度，列出所有相關的具體因素。
每個因素必須：
- 只屬於一個維度（互斥性檢查）
- 有足够的詳細程度（避免「其他」這類模糊歸類）
- 有明確的問題描述（包含具體表現和影響）

### Step 3: 自我 MECE 驗證
完成初稿後，執行以下驗證：
□ 窮盡性檢查：還有其他維度未納入嗎？
□ 互斥性檢查：有沒有子項同時屬於多個維度？
□ 深度檢查：是否有維度過於膚淺而忽略重要因素？
□ 一致性檢查：所有子項的詳細程度是否一致？

### 常見錯誤避坑指南
❌ 不要忽略測試驗證層面 — 這是常見的盲區
❌ 不要忽略文檔層面 — 規範缺失是隱性風險
❌ 不要忽略環境層面 — 瀏覽器/設備/快取差異經常被遺漏
❌ 不要將「缺少工具」放入技術層面 — 這是工具層面問題
❌ 不要將「缺少流程」放入技術層面 — 這是流程層面問題
❌ 不要因為「本次不涉及」而刪除整個維度 — 應標註「不適用」並說明理由
❌ 不要把同一個問題拆分到多個維度 — 選擇最精確的歸屬

### 輸出格式
每個維度使用以下格式：
【維度名稱】
  [✓] 已驗證 / [?] 需複核 / [✗] 存在風險
  - 子項 1：具體描述
  - 子項 2：具體描述
  ...

最後輸出 MECE 驗證結果摘要。
```

## 2. 場景特定前置引導

### 2-A. Bug 根因分析場景

```markdown
[場景特定補充 — Bug 根因分析]

你正在分析一個已發現的 Bug。請特別注意以下高遺漏率維度：

**已知高遺漏維度（根據歷史數據）：**
- 測試驗證層面：40% 的 Bug 分析遺漏此維度
- 文檔層面：30% 的 Bug 分析遺漏此維度
- 環境層面：25% 的 Bug 分析遺漏此維度

**請特別檢查：**
1. 是否有自動化測試可攔截此 Bug？
2. 是否有相關文檔應已記錄此類問題？
3. 是否在特定環境（瀏覽器/設備）下才會復現？
4. CI/CD 管道是否有可添加的檢查點？
```

### 2-B. 新功能設計場景

```markdown
[場景特定補充 — 新功能設計]

你正在設計一個新功能的實施方案。請確保以下方面都已納入考慮：

**必檢項目：**
- 數據模型是否需要變更？
- API 介面是否需要新增或修改？
- 前端組件是否需要新增或重構？
- 後端服務邏輯是否需要調整？
- 測試策略是否需要擴展？
- 使用者文檔是否需要更新？
- 數據遷移是否需要？
```

### 2-C. 風險評估場景

```markdown
[場景特定補充 — 風險評估]

你正在進行風險評估。請從以下角度全面掃描風險：

**必檢風險維度：**
- 技術選型是否成熟穩定？
- 第三方依賴是否存在安全漏洞？
- 性能是否滿足 SLA 要求？
- 數據完整性是否得到保障？
- 回滾方案是否可行？
- 是否符合法規合規要求？
```

## 3. 完整示例參考

### 3-A. 示例：完整的 MECE 拆解輸出

```markdown
═══════════════════════════════════════════════════════════════
  問題：卡片文字在淺色模式下需反白才可讀
═══════════════════════════════════════════════════════════════

【技術層面】
  [✓] 已驗證
  - CSS 選擇器權重競爭：Tailwind v4 where() 偽類與 html:not(.dark) 
    覆蓋規則進入權重競賽，行為不確定
  - ThemeContext 選擇器失配：ThemeContext 設置 class="light"，但
    初期修復嘗試選擇器 .light[data-theme="light"] 永不匹配
  - light mode CSS 覆蓋規則元素範圍不完整：初始覆蓋僅包含 h1-h4/p/div，
    缺少 label/span/button/strong/code/input 等常見元素
  - CSS cascade 優先級計算不確定性：@layer utilities 機制使覆蓋規則
    與 Tailwind 進入不確定性的權重競爭

【流程層面】
  [✓] 已驗證
  - 編碼階段無對比度檢查：開發者依賴肉眼判斷，未系統性切換淺色模式驗證
  - Commit 階段無 pre-commit hook 攔截：問題代碼可直接提交
  - PR 階段無 CI 質量 gate：無自動化檢查阻擋問題 PR
  - 測試階段無淺色模式系統性驗證：現有測試僅驗證暗色模式
  - 上線前無雙模式視覺審核 checklist：無強制性雙模式確認步驟
  - CAPA 關閉驗證標準未強制執行：所有 CAPA 均未完成手動視覺審核

【工具層面】
  [✓] 已驗證
  - 無 ESLint/Stylelint 配置：無編碼階段靜態檢查
  - 無對比度自動化校驗腳本：無法在提交前自動檢測低對比度
  - 無視覺回歸測試框架：無法自動檢測 UI 視覺變化
  - impeccable 檢測器 ignorePatterns 造成盲區：跳過 html:not(.dark)
    覆蓋規則導致其下方的實際問題未被檢測
  - 無 axe-core 無障礙自動化檢測：無法自動檢測可訪問性問題

【測試驗證層面】
  [✓] 已驗證
  - 無 Vitest 單元測試框架：核心組件無單元測試保護
  - 無 Playwright/Cypress E2E 測試：無端到端自動化測試
  - 無對比度自動化測試：無法檢測文字與背景的對比度
  - 無多瀏覽器兼容性驗證流程：未在不同瀏覽器中驗證

【文檔層面】
  [✓] 已驗證
  - 無標準化 CHANGELOG.md：版本變更記錄不完整
  - 無上線前檢查清單：無強制性發布前確認流程
  - 無 CAPA 與 git commit 關聯追蹤：問題追蹤與代碼變更脫節

【環境層面】
  [✓] 已驗證
  - 多瀏覽器兼容性驗證缺失：未在 Chrome/Firefox/Safari 中全面測試
  - 生產環境 CSS/JS bundle 快取策略：瀏覽器可能緩存舊版 bundle

═══════════════════════════════════════════════════════════════
  MECE 驗證結果：互斥 ✅ | 窮盡 ✅
  首次拆解遺漏維度：測試驗證層面、文檔層面、環境層面（共 3 個）
═══════════════════════════════════════════════════════════════
```

### 3-B. 錯誤示例：不符合 MECE 的拆解

```markdown
❌ 錯誤示例 A：維度遺漏
  只列出了技術層面和流程層面，完全遺漏了測試驗證層面、
  文檔層面和環境層面 → 窮盡性失敗

❌ 錯誤示例 B：子項重疊
  技術層面：「CSS 選擇器權重問題」
  工具層面：「Tailwind v4 選擇器機制問題」
  → 同一問題跨兩個維度 → 互斥性失敗

❌ 錯誤示例 C：描述模糊
  流程層面：「測試不充分」
  → 未指明是哪些測試、在什麼階段缺失 → 無法驗證
```

## 4. 快速檢查清單（Quick Check）

在輸出最終結果前，請逐一確認：

```
□ 所有 6 個標準維度是否都已評估（適用/不適用）？
□ 每個維度是否有至少 2 個具體子項？
□ 有沒有子項同時出現在多個維度？
□ 有沒有子項描述模糊（如「其他」「不夠好」）？
□ 有沒有明顯的情境被完全忽略？
□ 每個子項是否有足夠的詳細程度支持後續行動？
```
