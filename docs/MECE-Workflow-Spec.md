### 1.2 大模型 MECE 拆解常見能力缺陷清單

| 缺陷類型 | 描述 | 在 CAPA-005 中的體現 | 嚴重度 |
|----------|------|---------------------|--------|
| **D-01 維度遺漏** | 初始拆解時遺漏某個分類維度 | 遺漏「測試驗證層」「文檔層」「環境層」 | 🔴 高 |
| **D-02 子項重疊** | 同一層級下出現邏輯重疊的子項 | CSS 覆蓋規則問題與 Tailwind v4 權重問題本質相關但被分開列舉 | 🟡 中 |
| **D-03 层级混亂** | 不應在同一層級的項目被混在一起 | 「theme-context」與「css-cascade」分在不同維度但實為同一問題 | 🟡 中 |
| **D-04 假窮盡** | 看似完整但實際存在空白 | 3 層技術/流程/工具看似完整，實則遗漏測試和驗證層 | 🔴 高 |
| **D-05 語義模糊** | 分類標準不一致導致維度邊界模糊 | 「工具層」與「流程層」的邊界在 pre-commit hook 處模糊 | 🟢 低 |
| **D-06 深度不均** | 某些維度過深而其他維度過淺 | 技術層分析較深但流程層較淺，未延伸到審計層面 | 🟡 中 |

### 1.3 大模型能力邊界界定

```
┌─────────────────────────────────────────────────────────────────┐
│              大模型在 MECE 拆解中的能力邊界                       │
├──────────────────────────┬──────────────────────────────────────┤
│  ✅ 強項                 │  ❌ 弱項                              │
├──────────────────────────┼──────────────────────────────────────┤
│  基於已知模式的類比       │  發現真正新的維度                    │
│  熟悉領域的深度分析       │  跨領域的維度創新                    │
│  快速生成結構化輸出       │  保證窮盡性的自我驗證                │
│  多角度交叉檢查思路       │  識別自身邏輯盲點                    │
│  格式化文檔生成           │  持續一致性校準                      │
├──────────────────────────┼──────────────────────────────────────┤
│  需要外部補強的環節       │  需要人工介入的環節                  │
├──────────────────────────┼──────────────────────────────────────┤
│  MECE 維度完整性校驗     │  專業領域的窮盡性判斷                 │
│  子項互斥性檢查          │  業務合規性的最終確認                  │
│  輸出格式標準化          │  複雜情境下的優先級裁量                │
│  歷史案例比對            │  新類別問題的分类框架构建             │
└──────────────────────────┴──────────────────────────────────────┘
```

**核心結論**：大模型的 MECE 拆解屬於「模式驅動型」而非「演算法確保型」。它依賴訓練數據中的模式匹配來生成結構化輸出，但無法保證穷盡性——特別是在跨領域或新情境下。因此需要建立「外部補強流程」來填補這個能力 gap。

## 3. 前置引導流程

### 3.1 Pre-Injection Prompt 框架

在大模型執行 MECE 拆解任務前，自動注入結構化提示詞：

```markdown
# MECE 拆解前置引導（自動注入）

## 任務理解
你正在執行 MECE（Mutually Exclusive, Collectively Exhaustive）結構化拆解任務。

## 步驟化指令

### Step 1: 確定分析維度
在你開始分析之前，請從以下標準維度中選擇适用的維度組合：
- 技術層面（代碼/配置/架構）
- 流程層面（開發/測試/部署/審核）
- 工具層面（lint/測試/CI/檢測器）
- 測試驗證層面（單元/集成/E2E/可訪問性）
- 文檔層面（規格/規範/日誌/報告）
- 環境層面（瀏覽器/設備/部署/快取）

### Step 2: 窮盡性自我檢查
在完成初稿後，逐個核對：
1. 是否還有其他維度未被納入？
2. 每個維度內是否還有未分析的子項？
3. 是否有明顯的情境被忽略？

### Step 3: 互斥性檢查
確認每個子項只屬於一個維度，避免重疊。

### 常見錯誤避坑指南
- ❌ 不要在技術層面分析「缺少測試框架」——這是流程/工具問題
- ❌ 不要將同一問題拆分到多個維度
- ❌ 不要因為「暫不涉及」而省略整個維度
- ❌ 不要忽略「環境層面」（瀏覽器/設備/快取）
- ❌ 不要遺漏「文檔層面」（規範/報告/日誌）
- ❌ 不要將「測試」僅視為一個子項，它應作為獨立維度

### 輸出格式要求
按維度分層呈現，每個子項標註 MECE 驗證狀態：
- [✓] 已驗證通過
- [?] 需人工複核
- [✗] 存在重疊或遺漏風險
```

**自動化流程描述**：

```python
# 伪代码：模板匹配與補全算法
def layer1_verification(model_output: MECEOutput) -> VerificationReport:
    # Step 1: 場景分類
    scenario_type = classify_scenario(model_output.problem_description)
    
    # Step 2: 載入對應模板
    template = load_template(scenario_type)  # from mec-template-library.json
    
    # Step 3: 逐維度比對
    gaps = []
    conflicts = []
    for dimension in template.dimensions:
        model_items = model_output.get_items(dimension.name)
        template_items = dimension.checklist
        
        # 檢查遺漏
        missing_items = set(template_items) - set(model_items)
        if missing_items:
            gaps.append({
                'dimension': dimension.name,
                'missing': list(missing_items),
                'severity': 'HIGH' if len(missing_items) > 2 else 'MEDIUM'
            })
        
        # 檢查重疊
        overlap_items = find_semantic_overlap(model_items, template_items)
        if overlap_items:
            conflicts.append({
                'dimension': dimension.name,
                'overlapping': overlap_items
            })
    
    return VerificationReport(gaps=gaps, conflicts=conflicts)
```

## 6. 效果驗證標準

### 6.1 核心評估指標定義

| 指標 | 定義 | 計算方式 | 目標值 |
|------|------|---------|--------|
| **要素遺漏率** | 模板中应有但實際未出現的子項比例 | 遺漏子項數 / 模板總子項數 | ＜ 5% |
| **維度衝突率** | 出現邏輯重疊的維度對比例 | 衝突維度對數 / 總維度對數 | ＜ 10% |
| **業務貼合度** | 評審員認為「切中要害」的維度比例 | 認可維度數 / 總維度數 | ＞ 85% |
| **首次通過率** | 無需進入 Layer 2 評審的比例 | 直接通過數 / 總案例分析數 | ＞ 60% |
| **平均評審時長** | 從初始輸出到最終確認的平均時間 | 總評審時間 / 案例數 | ＜ 30 分鐘 |
| **核心漏洞发生率** | 經過 MECE 拆解後仍漏掉的根本原因比例 | 後續發現的根因 / 總根因數 | 降低 60% |

### 6.2 基線數據（優化前）

基於 CAPA-005 案例分析，確立以下基線：

| 指標 | 基線值 | 測量方法 |
|------|:------:|---------|
| 要素遺漏率 | 50% | 3 個維度（測試驗證/文檔/環境）完全遺漏 |
| 維度衝突率 | 15% | 技術/工具層面部分重疊 |
| 業務貼合度 | 70% | 技術分析深度足夠但驗證層面薄弱 |
| 首次通過率 | 0% | 所有案例均需多輪人工補充 |
| 平均評審時長 | ~60 分鐘 | 包含多次往返溝通 |
| 核心漏洞发生率 | 100% | 6 個根因中漏掉 3 個（50% 漏检率） |
